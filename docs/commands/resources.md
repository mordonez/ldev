# Resource Commands

The `ldev resource` namespace treats structures, templates, ADTs, fragments, Liferay Object Definitions and picklists as reviewable files. Every subcommand supports `--json`/`--ndjson` and the root accepts `--preflight` to check API surface reachability before running.

```bash
ldev resource --preflight export-structures --all-sites
```

## Read and inspect

```bash
ldev resource structure --site /global --structure BASIC-WEB-CONTENT
ldev resource template --site /global --template MY_TEMPLATE
ldev resource adts --site /global
ldev resource adt --site /global --display-style ddmTemplate_33994
ldev resource fragments --site /global
ldev resource object --object UB_COURSE
ldev resource picklist --picklist UB_LEVELS
```

- `structure` — accepts `--structure`
- `template` — `--template` accepts id, key, ERC or visible name
- `adt` — filter by `--adt`, `--id`, `--name`, `--display-style`, `--widget-type`, or explicit `--class-name`
- `adts` — list all ADTs for a site; add `--include-script` to include template scripts in JSON
- `fragments` — list fragment collections and entries for a site
- `picklist` — `--picklist` accepts ERC, name or numeric id; returns entry keys and the portable picklist
- `object` — `--object` accepts ERC, name (`Course` or `C_Course`) or numeric id; returns fields, relationships, referenced picklists and the portable definition

## Export

```bash
ldev resource export-structure --site /global --structure MY_STRUCTURE
ldev resource export-structures --site /global
ldev resource export-structures --all-sites --check-only
ldev resource export-template --site /global --template MY_TEMPLATE
ldev resource export-templates --all-sites --continue-on-error
ldev resource export-adt --site /global --adt MY_ADT --widget-type asset-publisher
ldev resource export-adts --all-sites
ldev resource export-fragment --fragment BASIC_COMPONENT-paragraph --site /global
ldev resource export-fragments --all-sites
ldev resource export-object --object UB_COURSE
ldev resource export-picklist --picklist UB_LEVELS
```

Key flags:

- `--all-sites` — export from every accessible site in one pass
- `--check-only` (structures export) — report diffs against local files without writing them
- `--continue-on-error` — do not abort the whole export if one entry fails
- `--dir <dir>` — override the default destination path resolved from `.liferay-cli.yml`

## Import

```bash
ldev resource import-structure --file path/to/structure.json --structure MY_STRUCTURE --check-only
ldev resource import-structure --file path/to/structure.json --structure MY_STRUCTURE --create-missing
ldev resource import-template --template MY_TEMPLATE --file path/to/template.ftl
ldev resource import-adt --file path/to/adt.ftl --create-missing
ldev resource import-fragment --fragment BASIC_COMPONENT-paragraph
ldev resource import-fragments --all-sites
ldev resource import-structures --check-only
ldev resource import-templates --apply
ldev resource import-adts --apply --continue-on-error
```

For singular template imports, `--site` is optional when `--file` already lives under `liferay/resources/journal/templates/<site>/...`; `ldev` uses that folder to resolve the target site.

Common flags on plural imports:

- `--apply` — import every local item for the resolved site
- `--all-sites` — import for every local site directory
- `--structure <key>` / `--template <key>` / `--adt <key>` — repeatable, scoped imports
- `--check-only` — preview only, do not mutate
- `--create-missing` — create the resource when it does not exist
- `--continue-on-error` — do not stop the batch on a single failure

Structure imports additionally accept the migration options:

- `--migration-plan <file>` — attach a migration plan or a descriptor generated by `migration-init`
- `--migration-phase pre|post|both`
- `--migration-dry-run` — do not persist structured content migration changes
- `--cleanup-migration` — blank the source fields after mapping them
- `--allow-breaking-change` — allow field removals without a migration plan
- `--skip-update` — validate only, do not update the structure definition

For migration-required changes, prefer `migration-pipeline`. `import-structure
--migration-plan` is the lower-level path used by the pipeline and for focused
debugging; it validates the plan before applying a breaking transition.

## Liferay Objects

Object Definitions are company-scoped, so object commands take no `--site`. Files
live under `paths.objects` (default `liferay/resources/objects/<ERC>.json`) and
are keyed by `externalReferenceCode`.

```bash
ldev resource export-object --object UB_COURSE
ldev resource import-object --object UB_COURSE --check-only
ldev resource import-object --object UB_COURSE
ldev resource import-object --file liferay/resources/objects/UB_COURSE.json --create-missing
```

- The exported file is portable: no ids, dates or status, no system fields, no
  reverse relationships. Object actions, layouts, views and validation rules are
  not managed by these commands.
- `--check-only` returns `changes` (`add`/`change`/`remove` per property, field
  and relationship) without writing.
- Before writing, the import checks that referenced picklists
  (`listTypeDefinitionExternalReferenceCode`) and relationship targets
  (`objectDefinitionExternalReferenceCode2`) exist.
- Custom fields present in the portal but missing from the file would be
  deleted with their data; the import refuses unless `--allow-breaking-change`.
- Relationship fields (`r_*`, business type `Relationship`) belong to their
  relationship and are not part of the file; derived relationship data
  (`objectField`, `objectDefinitionName2`, ...) is dropped too.
- Relationships are created or updated by name. The portal's definition update
  deletes forward relationships missing from its body, so ldev always sends the
  complete set: relationships that only exist remotely are kept, never deleted.
- Fields and relationships are matched by `externalReferenceCode` on update;
  when the file omits it, ldev reuses the remote one of the same name.
- Headless `*_i18n` maps use BCP 47 keys (`en-US`). Translations for locales the
  portal does not enable are dropped by the portal, and the read-back reports it.
- `--create-missing` creates the definition and publishes it.
- After writing, the definition is read back and compared with the file; any
  difference fails the command.

### Picklists

Picklists (list type definitions) follow the same rules and live under
`paths.objects/picklists/<ERC>.json`. Import them before the objects that
reference them; `import-object` fails when a referenced picklist is missing.

```bash
ldev resource export-picklist --picklist UB_LEVELS
ldev resource import-picklist --picklist UB_LEVELS --check-only
ldev resource import-picklist --picklist UB_LEVELS --create-missing
```

- Entries are matched by `key`, the value object entries store.
- Removing an entry from the file would delete it remotely and orphan stored
  values; the import refuses unless `--allow-breaking-change`.

## Company-level design resources

Company-wide design resources live in the global site (`/global`), which is the
default `--site` for style books.

```bash
ldev resource style-book --style-book UB_BRAND
ldev resource export-style-book --style-book UB_BRAND
ldev resource import-style-book --style-book UB_BRAND --check-only
ldev resource import-style-book --style-book UB_BRAND
ldev resource import-style-book --file liferay/resources/style-books/global/UB_CAMPUS.json --create-missing
ldev resource import-fragments --site /global
```

- Style books are files under `liferay/resources/style-books/<site>/<ERC>.json`
  with `externalReferenceCode`, `name`, `styleBookEntryKey`, `themeId` (for
  example `classic_WAR_classictheme`) and `frontendTokensValues`.
- `--check-only` reports `add`/`change`/`remove` per token; after writing, the
  style book is read back and compared token by token. Style book names are
  unique per site; the portal rejects a duplicate on create.
- They go through JSONWS `stylebook.stylebookentry`: on DXP 2026.q3 the
  `headless-admin-site` style-book, page and display-page-template endpoints
  answer `UnsupportedOperationException` unless feature flag `LPD-35443` is
  enabled, and that flag is not supported in production.
- Fragment imports into `/global` fall back to an auto-deploy zip. On DXP 2026 the
  global site's group key is the company id rather than `Global`; ldev reads the
  real key and waits until the fragments appear in the site, reporting the ones
  that do not as errors instead of assuming success.
- Display page templates at company level have no API that works without
  `LPD-35443`; ship them in a site initializer for now.

## Site initializers

`apply-site-initializer` creates a site from a site initializer (a
`siteInitializer` client extension or a `site-initializer/` folder) by site ERC,
then reads back what it declared.

```bash
ldev resource apply-site-initializer --source ub-facultat --check-only
ldev resource apply-site-initializer --source ub-facultat
ldev resource apply-site-initializer --source ub-facultat --site-erc FAC_FILOLOGIA --site-name "Facultat de Filologia" --friendly-url-path /filologia
ldev resource apply-site-initializer --source ub-facultat --site-erc FAC_FILOLOGIA --recreate
```

- `--site-erc`/`--site-name` default to `siteExternalReferenceCode`/`siteName` in
  the client extension's `client-extension.yaml`; pass other values to apply the
  same initializer to N sites.
- Site initializers are create-only: only creating a site runs them, redeploys
  and site updates do not re-apply pages, menus or templates. An existing site
  is refused unless `--recreate`, which **deletes the site and its content** and
  creates it again.
- Before touching the portal it lints silent failures: `page-definition.json`
  without `"type": "Root"` (error), navigation menus using
  `siteNavigationMenuItems` instead of `menuItems`, `numberOfItems` below
  `numberOfItemsPerPage`, and `fieldKey: "Title"` (warnings).
- `--check-only` reports the declared pages, menus and display page templates,
  the lint, and whether the site would be created, recreated or is blocked.
- After creating the site it reads back pages (by friendly URL), navigation menus
  (and their item counts) and display page templates. Display page templates are
  read through `headless-admin-site`, which needs feature flag `LPD-35443`;
  without it the result says they could not be verified.
## Redirects

`import-redirects` applies a redirect map, such as the 301 map a content
migrator generates, to one site (Liferay Redirect, JSONWS
`redirect.redirectentry`). Entries are keyed by (site, source URL).

```bash
ldev portal inventory redirects --site /facultat-filologia
ldev resource import-redirects --site /facultat-filologia --file redirects.csv --check-only
ldev resource import-redirects --site /facultat-filologia --file redirects.csv --probe
```

- `--file` is a CSV `source,destination[,permanent]` (header optional) or a JSON
  array of `{sourceURL, destinationURL, permanent}`. `permanent` defaults to true
  (301); `false`, `0`, `302` or `no` make it a 302.
- Source URLs are stored relative to the site without the leading slash and are
  served at `/web/<site>/<source>`; ldev normalises `/old/page` to `old/page`.
- The map is validated first: duplicate sources, empty sources or destinations,
  and redirects to themselves are rejected before touching the portal.
- `--check-only` reports `create`, `update`, `unchanged`, and `remoteOnly`
  (redirects in the site that the map does not mention; they are never deleted).
- After applying, every entry is read back; `--probe` also requests each source
  URL without following redirects and expects 301/302 to the destination.

## Migration

```bash
ldev resource migration-init --site /global --structure MY_STRUCTURE --templates
ldev resource migration-pipeline --migration-file path/to/MY_STRUCTURE.migration.json --check-only --migration-dry-run
ldev resource migration-pipeline --migration-file path/to/MY_STRUCTURE.migration.json
ldev resource migration-pipeline --migration-file path/to/MY_STRUCTURE.migration.json --run-cleanup
```

Use `migration-pipeline` as the default command for real migrations — it is the
full validated workflow.

The migration output includes a `reasonBreakdown` per migrated structure with counters for:

- `copiedToNewField`
- `alreadyHadTargetValue`
- `sourceEmpty`
- `noEffectiveChange`
- `sourceCleaned`

Progress messages localize title updates and report per-structure progress so large runs remain readable.

Flags worth remembering:

- `migration-pipeline --check-only --migration-dry-run` is the safest validation path
- first proof migrations should keep legacy fields and run without cleanup
- `migration-pipeline --run-cleanup` runs the cleanup phase defined in the same descriptor after explicit approval
- `migration-pipeline --skip-validation` skips the final check-only pass
- `migration-pipeline --create-missing-templates` creates descriptor templates when absent
- `--liferay-timeout-seconds 300` is useful for slow structure/migration calls; repeated runs can use `LIFERAY_CLI_HTTP_TIMEOUT_SECONDS` or `liferay.oauth2.timeoutSeconds`

See the [Resource Migration Pipeline workflow](/workflows/resource-migration-pipeline) for an end-to-end example.
